# 评测集：Codex 的黑话有没有被讲成人话

改提示词、换模型、调阅读等级时，用这套用例回答两个问题：

1. **更好懂了吗？** 不写代码的人读译文，是不是比读原文更容易明白现在的状态、自己要不要做什么。
2. **还对吗？** 讲成人话之后，有没有丢掉关键信息，或者说错。

第一个问题是目的，第二个是底线。

## 用例

23 条，放在 `cases/`：

- **19 条需要改（`type: "fix"`）**：真的难懂的 Codex 回复。来源包括本机会话、linux.do 吐槽帖、shuorenhua 评测集和 share-codex 数据集，详见 [SOURCES.md](SOURCES.md)。
- **4 条对照组（`type: "keep"`）**：本来就好懂。用来测翻译器会不会越帮越忙。

每条用例是一个 Markdown 文件，开头是一段 JSON，后面是原话：

```markdown
<!--
{
  "id": "close-to-disk",
  "type": "fix",                        // fix：需要讲成人话；keep：对照组
  "kind": "report",                     // report：最终汇报；summary：执行中的进度说明
  "question": "夜间任务现在会自动清掉过期文件了吗？",   // 用户当时问的
  "source": "出处",
  "checks": [                           // 2–4 个读完必须能答对的问题
    { "q": "昨晚删了多少文件？", "a": "一个都没删，只列出了 11 个待清理文件。" }
  ],
  "traps": ["说已经删掉了 11 个文件"]    // 可选：已知容易犯的错
}
-->

这块给你收口落盘了……
```

全局黑话词表在 `words.json`，所有用例共用，不再每条单独列。`hard` 表里的词只要出现就算黑话；`soft` 表里的词在技术语境里常有正当用法，只统计、不计分。

## 怎么跑

```bash
node eval/run.mjs                                    # 全部用例，简明改写 + 讲给外行
node eval/run.mjs --case close-to-disk --modes deep  # 单条
node eval/compare.mjs results/旧.json results/新.json # 改版前后，哪份更好懂
node --test eval/lib.test.mjs                        # 评测脚本自己的测试
```

被测对象是 `src/backend.js` 的 `translate()`，和插件运行时走同一条路径。密钥从 `~/.config/minicode/siliconflow.env` 读取，也可以用环境变量 `SILICONFLOW_API_KEY` 覆盖。默认评审模型是 `deepseek-ai/DeepSeek-V4-Pro`，和被测的 Flash 不是同一个模型。

## 怎么评分

| 指标 | 怎么算 | 用在 |
|---|---|---|
| **比原文好懂** | 评审拿原文和译文比较，然后对调位置再比一次，两次都选译文才算「胜」 | 需要改的 |
| **黑话残留 / 新增** | 用 `words.json` 的 hard 表比对原文和译文：原文的黑话译文还剩几个，译文又自己加了几个 | 全部 |
| **读得对** | 评审只看译文，逐条判断能不能答对 checks（部分答对算一半） | 全部 |
| **说错** | 答出错误结论、踩中陷阱、写了原文没有的内容，三项合计。「多写了」的条目必须逐字摘自译文，评审编造的引文会被丢掉 | 全部 |
| **对照组改动** | 原文和译文的字面重合度，1.00 表示一字未改 | 对照组 |

前两项回答「更好懂了吗」，后两项回答「还对吗」。逐条事实保留下来了，但简化成每条用例 2–4 个关键问题，只用来守底线。

改提示词时，先跑一遍旧版、再跑一遍新版，然后用 `compare.mjs` 直接比两份译文。改版前后的对比比任何绝对分数都可靠。

## 当前基线

[results/2026-11-26-baseline.md](results/2026-11-26-baseline.md)，插件默认模型，23 条用例：

| 等级 | 比原文好懂 | 读得对 | 说错 | 黑话残留 | 对照组读得对 | 对照组说错 |
|---|---|---|---|---|---|---|
| 简明改写 `light` | 13 胜 / 6 平 / 0 负 | 100% | 0 | 5 / 49 | 100% | 0 |
| 讲给外行 `deep` | 9 胜 / 8 平 / 2 负 | 88% | 11 | 2 / 49 | 72% | 6 |

- **简明改写在真正晦涩的用例上是有效的**：49 个硬黑话只剩 5 个，没有说错。之前觉得它「几乎不改」，是因为旧用例里有不少本身就不难懂。
- **讲给外行的问题出在「还对吗」**：one-more-cut 把用户的提问当成了结论，写成「先给结论：已经少拷一次了」，事实正好相反；buried-skip 只剩 38% 的关键信息；对照组的事故复盘丢了一半信息。它还经常给原文没有的步骤补上「谁来做、怎样算通过」，这条来自它的提示词。
- 同一套用例连跑两次，讲给外行的「好懂」有 6 条结果变了（第一次 13 胜，第二次 9 胜），简明改写比较稳。用例数量少，三四个胜场的差别不说明问题。比较改版前后时，至少跑两次，或者直接用 `compare.mjs` 看逐条差异。

## 局限

- 「好懂」是模型代替人在判断。对调位置能过滤掉一部分随机偏好，但评审有时还是会给出离谱理由，比如认为「收窄、坐实」比「缩小、确认」更口语。最后应该由真人来评，这是下一阶段的事。
- 英文原文的用例译成中文，「比原文好懂」天然占优，这两条主要看「读得对」和「说错」。
- 「黑话」是按词表匹配的。词表没收的新说法抓不到，所以发现新口癖时要补进 `words.json`。

## 和插件构建的关系

插件的缓存哈希只计算 `package.json` 和 `src/`（见 `src/translation-cache.js`），所以改 `eval/` 不会让用户的译文缓存失效，也不会触发重新授权。
